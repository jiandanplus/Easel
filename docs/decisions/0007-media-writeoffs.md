# 0007 媒体任务也走审计过的平台承担（迁移 021）

日期：2026-11-06 · 状态：已实施，随 P3 上线（用户确认）

## 背景
生产有一笔 10-27 的图片任务 `81a6155d…`：上游已生成，但当时媒体目录只读，写盘失败，用户没收到图，任务停在 `pending_reconciliation`，预留 1,000,000 点。用户决定释放这笔预留。现有工具都做不到：控制台核算页只记审核意见；主机侧 `execution-writeoff-*` 只认文本任务；`media_jobs` 的状态里也没有 `waived`。唯一的“办法”是手写 SQL 改账，这会绕开审计和守恒检查。

## 决定
新增迁移 021 和 `media-writeoff-plan / apply / operation`，完全沿用 012 文本承担的规则：
- 只读生成计划，绑定任务、预留、scope 摘要、存储预算的快照；操作者审核计划哈希后才能 apply，apply 在原锁序下重新核对快照。
- 只处理已派发、租约已过期、没有 receipt、没有终态证据、没有活跃异步任务（`media_work` 不存在或为 `manual`）的待核算任务。
- 客户收费 0，`actual` 保持 NULL，供应商用量仍未知；不伪造用量，不重新生成，不恢复产物。
- 同一事务内释放点数预留与存储预算，任务标为 `waived`、`delivery_state=unavailable`；处置记录不可改、不可删，数据库在提交时独立复核整批记录。
- 只有通过 schema owner 校验的主机入口拥有能力；runtime 与 Console 对两张处置表没有任何权限，启动检查也会拒绝。

## 影响
- P3 迁移从 017–020 变为 017–021。021 只扩展状态与检查函数，并新建两张表，不改已有数据。
- 承担后该任务暂存的产物不再被钉住，按正常过期回收。
- 运营处置仍是发布之后的独立步骤：发布本身不会释放任何预留。
