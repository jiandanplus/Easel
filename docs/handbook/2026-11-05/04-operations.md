# 04 · 维护与故障处理

维护目标是保持唯一身份与账本权威、保留用户数据，并使错误能按原任务恢复。下文标为只读的操作不调用模型；发布、授权、发点、核销、清理、重启与恢复均需绑定当次准确对象和维护计划。

## 1. 日常巡检

| 频率（建议） | 检查 | 出现异常时 |
| --- | --- | --- |
| 自动周期／每日查看 | API、Console、隧道、Nginx、PG、Logto，health 与静态资产 | 先定位失效层，保存安全状态 |
| 每日 | 新备份密文、timer、任务结果、权限、新鲜度 | 区分“没有备份”和“有密文但未验证恢复” |
| 每日 | 磁盘、inode、内存、连接数、媒体增长 | 暂停新增重型演练，定向处理可删除资源 |
| 每日／按业务量 | 待核算数量、最早时间、未知费用、异常订单 | 按原请求调查，不清账解锁 |
| 每周 | 证书续期、上游余额／额度、模型目录和错误趋势 | 先验证配置，再计划变更 |
| 每次发布前／定期 | 完整隔离恢复与业务验证 | 不直接覆盖生产重建 |

154 曾安装 `easel-health-watch.timer` 每 5 分钟探测，写 `/var/lib/easel-health/status.json`；原实现只在告警变化时记 journal，没有外部通知。历史阈值：备份超过 30h warning／48h error，根盘 80%／90%，MemAvailable 512MiB／256MiB，证书剩余 14d／3d。详见 [健康检查手册](../../../services/platform/deploy/HEALTH-WATCH.md)。这些是已有探针阈值，不能代替业务容量承诺。

本机发起的只读定位命令：

```bash
rtk proxy ssh -o StrictHostKeyChecking=yes easel-zhiyin \
  'systemctl is-active easel-central-production.service easel-console-production.service nginx.service easel-health-watch.timer'
rtk proxy ssh -o StrictHostKeyChecking=yes easel-zhiyin \
  'systemctl list-timers --all --no-pager'
```

深入查看日志在服务器私有终端进行，仅提取错误类别、时间和关联 ID。不要把完整 journal、SQL、响应正文、账户信息或配置贴进公开交接材料。

## 2. 模型目录更新：完整操作顺序

New API 新增模型不会自动使该模型成为 Easel 当前账号的可用订阅模型。更新分为供应端、中央目录和用户授权三部分。

### 2.1 供应端

1. 在 New API 配置对应渠道，核对真实供应商模型名、协议、分组、状态与额度。
2. 核对 Easel 使用的**业务令牌**允许该分组／模型。渠道中填写的供应商 Key 与 New API「令牌」菜单生成的业务令牌不同；管理 PAT 也不能代替模型业务令牌。
3. 用服务端私有令牌读取可见模型，核对列表和路由；读取目录不证明真实调用可用。
4. 对文本验证 Responses／流式／工具循环／可信用量；对图片验证生成、下载、解码、尺寸与计量；对异步媒体验证 submit–poll–download–cancel 全生命周期。

真实探针可能收费，先固定单次请求和范围，记录请求摘要、时间与原 task ID；超时或应答不明不自动重试。业务 Key 留在服务器，不放浏览器、本机普通文件或聊天。

### 2.2 中央映射与发布

1. 核对 `CENTRAL_EXECUTION_CONFIG_FILE` 或媒体私有配置中的 provider ID／version、固定 endpoint、公开模型到上游模型映射。
2. 准备不可变模型定义：产品、功能、provider、能力、费率、限制和验证引用。费率／协议变化发布新版本，不改已有任务快照。
3. 文本模型用现有 CLI；以下为形状，不代表本次实际执行：

```bash
rtk proxy uv run --project services/platform --frozen \
  --env-file /ABS/PRIVATE/central-operator.env \
  python -m platform_service model-publish \
  --file /ABS/PRIVATE/model-v2.json --operator YOUR_OPERATOR_ID
rtk proxy uv run --project services/platform --frozen \
  --env-file /ABS/PRIVATE/central-operator.env \
  python -m platform_service model-enable --model YOUR_MODEL_ID --operator YOUR_OPERATOR_ID
```

4. 服务器实际操作使用本次固定 release 运行环境和真实受限配置。映射变更按发布流程重启，不能将旧任务重绑到新供应商。
5. 媒体使用独立 `MediaService.publish` 合同和受审部署入口；没有通用媒体 CLI 时不要编造命令或直接手改表。先按 [媒体合同](../../../services/platform/MEDIA.md) 准备计划。

### 2.3 权益与用户界面

核对模型是否启用、产品是否允许、当前套餐是否包含对应功能、点数模式是否匹配，以及点数和准入限制。测试额度、内部体验和商业额度各自遵守合同，不能互相挪用。

登录原用户后重新加载账号目录，在输入框右下角选择模型：文本对应 `GET /v2/products/easel/models`，媒体对应 `GET /v2/products/easel/media-models`。这些接口需要产品会话，不提供把 token 粘到浏览器的操作步骤。强度仅在模型明确声明支持时显示可选档位。

最后用现有余额做一笔限定真实验收，对照原执行 ID、实际回复／产物、用量、预留释放和钱包差额；不能为了验收重复发点。自定义模式则在本机设置中选择自定义供应商，更新其自己的目录与能力，不消耗中央钱包。

## 3. 登录失败、白屏或过期

按从浏览器到身份服务的顺序检查：

1. **链接过期：** 回工作台头像或后台首页发起新登录。不要刷新／重复提交旧 callback，也不要传播包含 code／state 的 URL。历史登录事务期限为 5 分钟，以实际配置为准。
2. **login 白屏／转圈：** 核对当前域名 DNS／TLS、静态资源、Logto／身份 PG 和代理，不将“本机页面 200”当成身份系统正常。
3. **回调 invalid_request：** 核对发起端事务是否仍存在、精确 origin／issuer／redirect URI、应用 ID、时间窗口和本次会话；用 correlation ID 定位，避免输出 code／secret。
4. **refresh_uncertain：** 先查询真实会话状态，保留本地私有文件；通过界面取消旧登录或重新发起。不要复制旧 refresh token 续接任务，也不要删全部历史解决登录。连接没建立成功（断网、握手失败）时请求没发出去，不算 uncertain，日志记 `refresh_not_sent`，下次自动重试；请求已发出但没收到回复时才会出现 uncertain。
5. **登录错账号／无管理员权限：** 退出该浏览器会话，使用独立管理员账号重新登录；产品登录不会提升后台权限。

后台只能用精确 `http://127.0.0.1:18885/`，先确认隧道仍运行。若是端口冲突，核对占用者，不能随意杀掉其他会话。

## 4. 模型不显示或接口失败

| 表现 | 优先核对 | 不应采取的处理 |
| --- | --- | --- |
| New API 有、Easel 无 | 业务令牌分组、中央映射／发布／启用、功能权益和账号目录 | 前端硬编码全部模型 |
| 目录有、400／不支持参数 | 原请求协议、模型能力、推理参数和工具格式 | 默认降级模型／静默改协议 |
| 401 | 业务令牌有效性、绑定和权限 | 在日志输出 Key 或用管理员 PAT 替代 |
| 流式中断 | 原 operation 终态、可信用量、缓存、代理缓冲和期限 | 自动新 key 重发付费请求 |
| 产物 URL 失效 | 原任务、允许下载来源、归属、已保存文件 | 附 Authorization 到任意外部 CDN |
| 只有任务 ID | 原 job 的 poll／终态与输出 | 将 ACK 当作生成成功 |

更新 provider binding、插件或价格后仍保留旧任务归属和冻结合同。重建新模型不能消除旧待核算。

## 5. 待核算队列与点数

“待核算请求已达上限”意味着该钱包的未知费用操作占用了待核算名额。查询是正确动作，清缓存、重新登录或改 UI 不会释放中央预留。

处置流程：

1. 私有 Console 打开待核算队列，核对准确用户／产品／钱包、job／attempt、provider binding、预留与实际用量状态。
2. 查看只读详情、原关联 ID、处理进度和审计。R1 工单状态变化不改变资金，也不等同完成核算。
3. 若有已持久化可信终态，按 R2 恢复原结算，不重新请求模型或执行工具。
4. 无可信费用时保持 actual=NULL。需要平台承担，应另作准确任务清单、影响、审批依据和幂等计划；只处理该计划。
5. 复核预留、余额、账本恒等式、审计与晚到证据处理；不删除旧记录。

历史批准的 3 笔 GLM 已有单独处置，授权不覆盖后续 Flare 或其他未知请求。具体 plan／apply／operation 命令见 [R2 处置手册](../../platform/reconciliation-r2-deployment.md)；本手册不发出新的核销授权。

## 6. 用户、套餐、管理员和支付

首次独立管理员在 Console 认证后产生申请编号，运营者核对准确申请，使用 `console-approve --request ... --role ... --operator ...` 授权，用户重新登录。禁止按名称猜人、重用过期申请或共享管理员密码。撤权使用 `console-disable` 并验证旧会话失效。

套餐用不可变定义发布，发放有稳定幂等键和来源审计。`grant-test` 的测试点数不能自动用于真实供应商；内部体验能力由独立受限策略控制，不是付款，也没有网页自助发点。更新套餐不应重发旧赠送或延长原有效期。

支付目前保持 `CENTRAL_PAYMENTS_MODE=disabled`。后续配置商户后，还须完成正式套餐价格／点数／有效期／退款条款、验签回调、主动查单、幂等入账、超时、退款和对账。不能通过 `test-payment` 伪造生产付款。操作详见 [支付运维](../../../services/platform/PAYMENTS.md)。

## 7. 备份、恢复与灾备

完整保护范围包括：中央业务库、Logto 身份库、角色及授权者、数据库设置／序列／扩展、安全配置、媒体文件及 registry、必要恢复密钥和版本清单。备份与密钥应有分别受限的保存与恢复路线；仅同机密文不能覆盖整机丢失。

| 阶段 | 已有范围 | 不能替代 |
| --- | --- | --- |
| 历史 R2 双库 | 有一次真实新隔离 PG 恢复及严格对照 | 后续迁移／媒体／应用／异地恢复 |
| B1 | 分块归档、完整文件清单和私有新目录恢复 | 真实数据库导入、快照窗口或加密认证 |
| B2 | 写入／GC 屏障、捕获、认证密文、落盘自验和组件验证 | 完整新 PG／应用恢复与生产 timer 验收 |
| B3 | 目标生命周期、worker、网络与多项重建源码子门 | 当前尚未完成的整套角色／数据库／媒体／应用恢复 |

**恢复演练顺序：** 冻结对应源范围与版本 → 验证受限密文与清单 → 在全新独占目标恢复角色／权限／数据库／配置／媒体 → 对照数据、序列、ACL、身份映射、账本和文件 → 以低权应用验证 → 记录故障与清理结果。目标无公网出口、无生产回调、无真实模型／支付派发，不能与生产同时花同一钱包。

B3 当前没有可交付的一键生产恢复命令；不要把开发 worker 或历史一次性脚本当成通用运维工具。没有完整当前范围恢复证据时，生产 timer 保持原方案，不因新密文自验成功就替换。

数据库恢复到旧时点后直接重新开放消费可能丢失已发生费用。生产前向恢复、PITR、写入截止与未知记录处理必须单独设计；保留失败目标、密文、清单和原审计，不自动重跑同一 nonce。

## 8. Docker 与磁盘清理

先区分服务器生产资源、本机其他产品和本次测试资源。镜像大小含共享层，删除后逻辑大小下降不等于 macOS 立即回收同等空间；Docker 虚拟磁盘和数据卷另占空间。

只读盘点，在资源所在机器运行：

```bash
rtk proxy docker system df
rtk proxy docker ps -a --no-trunc --format '{{.ID}} {{.Names}} {{.Image}} {{.Status}}'
rtk proxy docker image ls --no-trunc
rtk proxy docker volume ls
```

对候选逐个形成清单：完整 ID、任务用途、原验证是否结束、是否失败证据、挂载卷、镜像被哪些容器引用、是否还需后续重建。没有引用不自动意味着可删；停止的数据库也可能是唯一保留副本。

仅在确认精确对象后定向删除，下面是占位形状：

```bash
rtk proxy docker rm EXACT_STOPPED_TEST_CONTAINER_ID
rtk proxy docker image rm EXACT_UNREFERENCED_TEST_IMAGE_ID
```

不使用 `-f`、全局 prune 或 `--volumes`，不删除生产／用户数据卷、未交付制品和要求保留的失败现场。先保留报告与必要证据，再删除不用的成功辅助容器；后验比较容器、卷清单与磁盘，不把未知删除结果直接重试。

Docker 接口超时时先定位引擎状态，不靠连续 prune／kill 解锁。正常重启与强制结束进程对本机数据库影响不同，应按具体维护计划处理。

## 9. 桌面数据和升级排障

通用默认工作区为 `~/Library/Application Support/Easel/workspace`，启动日志为 `~/Library/Logs/Easel/launcher.log`；原 17868 可能使用历史验收工作区，必须读取其实际配置再保护。不要把默认目录当成原用户数据已迁移到这里的证明。

关闭网页不会停止后端；使用随包 `Stop Easel.command` 认证并停止自身实例。端口被占用先确认程序归属，不以 PID 猜测终止。包内 Python／Node／Pi 不自动装额外依赖；媒体工具缺失时应给出能力状态，不破坏固定运行时。

升级前后核对对话正文、附件、输出、登录身份范围、自定义接口配置、主题、模型选择和钱包元数据。令牌正常轮换不要求逐字节相同，不能把旧 token 复制回去；对受保护内容应使用哈希或私有快照比较。

## 10. 维护记录模板

每次维护填写：日期和执行人；目标主机／组件；原版本、迁移与状态摘要；准确动作及依据；制品／配置清单哈希；开始结束时间和原进程终态；数据／资金前后差异；失败与未知项；回退或前向恢复决定；资源清理清单；安全证据位置。

公开交接报告只放脱敏结论、版本和摘要，原日志／账本快照／备份等继续留在私有范围。
