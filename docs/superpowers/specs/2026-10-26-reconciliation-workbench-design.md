# 中央待核算运营工作台：R1 设计

状态：2026-10-26 用户已明确选择“按方案 A 开发 R1”，进入实施。此批准不包含补扣、释放预留或其他资金操作。

日期：2026-10-26（Asia/Shanghai）。分支继续使用 `codex/ui-redesign`，不合并 `main`，保留 Easel 自定义接口、订阅模式、既有账号和资金状态。本批设计留在工作区，不自动提交或推送。

## 目标与可见结果

运营者在现有私有 Console 中找到待核算请求、查看原预留和已知事实、登记处理进度，并追踪谁在何时以什么原因处理。用户端仍如实显示未知费用和原预留。

R1 的资金范围是只读：查询和登记处理进度均不调用模型、不查供应商、不补扣点、不释放预留，也不改变 execution job 的财务状态。工单状态与 `pending_reconciliation` 分开显示。金额未知始终为 `null`／“未知”。

## 已核对的实现与历史证据

- 上一阶段方案 A 已完成：执行并发与待核算分开，体验套餐执行并发仍为 1；同钱包 pending 达到 3 后拒绝新增操作。见 [方案 A](2026-10-25-pending-concurrency-proposal.md) 与 [验收报告](../../validation/2026-10-25-execution-stability.md)。
- 2026-10-25 最终验收快照中，旧 job `690ef707-da7f-4f8c-be18-1fdbf7645e40` 保留 9728 微点、`actual=null`；可用 9980757、已用 9515、累计发放 10000000 微点。这是历史基线，不代表今天刚刚查询的生产余额。
- `execution/core.py::finish()` 已支持 dispatched/pending 接受可信终态用量，原子更新 receipt、结果缓存、钱包、invocation 和 job；它是内部可信接口，不能直接接受浏览器自报 tokens 或 hash。
- 当前 Console 只有调用列表，执行记录详情仍直接展示列表行；没有专用待核算队列或处理流转。
- Console 数据库角色按列读取执行记录，没有钱包、job、receipt 的写权限，也不能读取 raw reason、scope、attempt、provider response ID 或结果正文。R1 保留这些限制。
- `console_operations` 和 `console_audit_events` 的现有动作约束针对目录操作。新工作流需要追加迁移和明确权限，不改写历史迁移。
- 旧请求没有持久化的精确上游请求关联；同期 New API 候选日志及估算 tokens 不能作为补结算凭据。新功能不能追溯制造旧请求标识。

## 三种推进方式

| 方式 | 本批产出 | 成本与边界 |
| --- | --- | --- |
| A：先运营工作台，再可信结算（推荐） | 待核算队列、独立详情、处理进度、不可变审计；资金只读 | 可直接使用现有受限 Console，先建立可验收的处理闭环；实际费用仍须后续可信凭据核定 |
| B：同批加入可信凭据采集和补结算 | 工作台加专用金融命令、凭据校验和原子结算 | 需先确定供应商凭据、精确 attempt 绑定、权限和仅费用结算协议；开发与验证范围更大 |
| C：先补新请求的上游关联，再建设工作台 | 持久化早期响应标识及安全诊断 | 优先改善未来请求可追踪性；不能补回旧请求缺失标识，也暂不改善运营者当前处理入口 |

建议批准 A 的 R1；B/C 所需的采证及资金命令形成后续 R2，另行明确设计与验收。不是把 R1 的进度登记包装成已结算。

## 入口与页面

在 Console“追踪与核对”中新增“待核算处理”。继续仅私有访问，不修改公开域名、安全入口或管理登录。

### 队列

- 默认显示财务状态为 pending 的当前请求；可查看具有处理历史的已结束请求。
- 分页及查询沿用现有有界协议：limit 1–100、offset 0–100000、q 最长 128；固定枚举筛选产品、资金模式、处理状态，值均服务端校验和参数化。
- 每行显示 job 标识、产品、模型、钱包、资金模式、原预留、实际费用、费率版本、创建时间、财务状态最后更新时间，以及运营处理状态。
- 不用更新时间冒称真实派发时间或首次进入 pending 时间。缺少的数据明确显示“未记录”。
- 空队列、无筛选结果、无权限和服务错误分别显示；失败时不将旧列表呈现为最新结果。
- 列表读取不创建工单、不写 last_seen、不调用过期入账或供应商。

### 详情

以 job ID 独立读取服务端详情，不能仅放大列表行。详情包括：

1. 当前财务状态、原预留、已知或未知实际费用、冻结费率、产品与资金模式。
2. 当前 Console 已获准读取的 tokens；缺失显示“未知”。
3. “中央用量记录存在／不存在”和已授权字段范围内的部分一致性诊断：只判断记录有无、与 settled 状态是否对应及允许读取的用量字段是否缺失。不能据此证明完整回执或精确 attempt 绑定，也不把记录存在升级为运营补结算许可。
4. 本次安全快照时间和摘要。该摘要仅绑定安全字段，名称明确为“核查快照摘要”，不是供应商可信证据 hash。
5. 当前处理状态及追加式处理历史，包含操作者、原因、时间与版本。
6. 钱包与预留的只读跳转。若钱包明细被截断，保留截断提示，不声称已审计全钱包。

R1 不读取或展示原始 prompts、模型输出、HTTP headers、keys、tokens、原始 reason、完整 Scope、上游响应正文或原始核账凭据。不为了详情而扩大上述原始列的 SELECT 权限，也不使用权限检查未覆盖的 view／SECURITY DEFINER 路径。

### 运营操作

允许登记三个处理状态：

| 处理状态 | 含义 | 资金影响 |
| --- | --- | --- |
| 核查中 | 运营者开始检查已有事实 | 无 |
| 等待凭据 | 现有事实不足，等待服务器或供应商提供精确凭据 | 无 |
| 存在争议 | 发现信息冲突，继续保留未知费用 | 无 |

未登记时显示“待处理”，不为了显示默认状态创建数据库行。没有“已核清”“释放预留”“强制结算”“重跑请求”按钮。

当业务服务随后独立完成原任务时，界面根据真实财务终态显示“财务已结束”，保留原处理历史；工单状态不能覆盖 job 状态。R1 不自动发送通知或外部消息。

每次进度登记必须提供有界原因、当前工单版本和同源 CSRF；原因长度 1–500 字符，拒绝控制字符，不提供上传原始凭据的字段。页面提示原因只填写处理说明。服务端 actor 来自管理会话，不能由浏览器指定。

## 服务与数据边界

新增独立模块 `console_reconciliation.py`，复用 Console 的会话复验、只读快照、分页、错误投影和幂等审计模式；不导入或调用 `ExecutionService.finish()`、`CreditLedger.settle()` 或 provider runtime。

拟定接口：

| 接口 | 行为 |
| --- | --- |
| GET `/api/reconciliation-cases` | 安全分页队列；默认 pending，工单缺失不写库 |
| GET `/api/reconciliation-cases/{job_id}` | 有界详情、快照摘要、处理历史；截断必须明确 |
| POST `/api/reconciliation-cases/{job_id}/reviews` | 仅登记处理状态；`state/reason/expected_revision/snapshot_hash`，Header `Idempotency-Key` |
| GET `/api/reconciliation-cases/{job_id}/review-operations` | Header `Idempotency-Key` 指定原键，仅查询当前 actor、目标 job 的已提交操作安全结果；不创建记录 |

列表复用 `{items,limit,offset,has_more}`。金额用十进制微点字符串，前端用 BigInt 格式化。详情不返回任意 SQL 结果或整行 JSON。

新处理记录只引用已经存在的 job；job／wallet／product 以服务端读取结果为准，浏览器不能重新指定归属。同一个 job 只有一个当前工单，处理事件追加且不可改删。

追加迁移创建一张当前工单元数据表与必要索引，处理历史复用既有不可变操作与审计，不重复建设完整事件表。在既有操作／审计约束中显式增加本批动作；保留既有动作、约束与历史记录。迁移编号以实施前的实际最大编号为准，不能覆盖旧迁移。

元数据只保存 job 引用、处理状态、版本、操作者、原因、核查快照摘要及时间，并用 `last_operation_id` 绑定最后一次不可变操作。数据库延迟约束检查 job、revision、state、actor、reason、snapshot_hash 与该操作目标及结果一致，缺少匹配操作／审计的首次创建或更新整笔失败；不锁定财务状态。不复制钱包资金分桶、原始回执、凭据或结果缓存。

核查摘要为服务端计算的版本化固定安全字段 canonical JSON SHA256，字段为 job ID、产品、钱包、模型、资金模式、财务状态、预留、actual、冻结费率、允许读取的用量、中央用量记录存在标记和财务 updated_at。排除 observed_at、当前时间、分页、显示文案和工单历史；金额、null、UTC 时间序列化规则固定。工单 revision 单独 CAS，不混入财务摘要。

## 权限与幂等

- 原管理读权限可查询队列与安全详情；产品 bearer 和普通注册账号不能访问。
- 新增仅用于处理元数据的 `execution:review`。admin/operator 可登记，viewer 只读；不把它命名为 `execution:reconcile`，不赋予金融权力。
- Console DB 角色只新增必要工单元数据与审计权限；新表按列限定 SELECT/INSERT，UPDATE 仅限当前状态、revision、操作者、原因、快照摘要及更新时间，不能更新 job 引用、创建时间或删行。仍不能改资金表、execution job、receipt、reservation、membership 或内部发点记录；产品 runtime 不因此获得 Console 处理记录的读取权限。
- 同事务重新检查会话、ACL、epoch；同源 Origin、CSRF 和严格请求字段集合继续生效。
- actor＋幂等键串行化；同键同内容返回原结果，不重复事件；同键不同内容返回409。记录原因、前后版本和安全快照 hash。
- 同工单 expected_revision 使用 CAS，无工单时 revision=0；两个首次登记只允许一个成功，失败不留空工单或孤立审计。冲突返回409并要求重新读取。重复幂等查询先返回原结果，不受后来 revision 变化影响。
- 应用显式锁只针对工单元数据，不为更新工单而授予 Console 对财务行的 UPDATE 权限。首次工单的外键可能取得正常 KEY SHARE 引用锁，并与真实结算路径的 FOR UPDATE 短暂竞争；锁超时必须整笔回滚，不保证财务路径完全无锁等待。
- POST 同事务重算当前安全投影摘要；不匹配或观察到 job 已不是 pending 时返回409。无需快照 TTL、客户端时间或签名 token。财务状态在只读检查后仍可能独立变化；进度事件只记录当时观察，不能声称锁定或阻止业务结算。页面始终以最新财务终态优先显示，任何这类竞态均不改变资金。

## 失败与缺失事实

- 无中央用量记录：仅证据提示区显示“尚无中央终态用量记录，需等待凭据”，不展示预计 actual=0。运营处理状态独立，未登记仍为“待处理”，不自动创建或更新工单。
- 账务诊断不一致：标记需核查，不能提供自动修复；显示本次检查范围，不能把部分明细和截断结果当作完整审计。
- 会话过期、权限撤销或 epoch 变化：拒绝写入；不创建半条工单或孤立审计。
- 幂等、revision 或快照冲突：明确409，保留输入原因供用户重新审阅，但不自动重提 POST。
- 网络中断：操作结果未知时只允许调用同 actor、job、原幂等键的操作结果 GET。没有已提交结果只表示“尚未观察到提交”，在途事务仍可能提交；不能当作原操作未执行，不能自动换键或补提 POST。操作结果查找不能从截断历史或当前工单 revision 猜测，也不能查询其他 actor 或 job 的键。
- 原旧任务仍保留9728微点和 `actual=null`，R1 工单元数据的变化不降低 pending 计数，不释放执行／资金权益。

## 验收

1. 真实隔离 PostgreSQL：查询无业务／工单写入；不存在工单不创建默认行；pending默认筛选、严格枚举、分页排序和跨钱包详情归属正确。
2. 真实受限角色：Console仍不能读原始私密列或改账；产品角色不能读新工单；异常新增权限使启动检查拒绝。
3. 权限和事务：普通用户／产品 bearer拒绝、viewer写入拒绝、会话／ACL／epoch即时复验、Origin与CSRF；审计失败时整个处理命令回滚。
4. 幂等与并发：同键同内容仅一个事件、异内容409、首次登记和CAS竞争只有一个新版本；响应丢失后同键GET可查、原POST仍在途时GET不假称失败、原事务回滚、其他actor/job键拒绝、后来revision变化仍返回原提交结果。原财务在检查前已终态拒绝，检查后独立变化只记录当时观察且资金写入为零。
5. 金融不变量：已知／未知费用正确；工单操作前后原钱包、hold、reservation、job、receipt、journal和entries不变；冻结、到期和超预算保持原规则。
6. 前端：null不变零、工单与财务状态分开、旧响应不覆盖新筛选、详情读取失败不显示列表行为成功、非授权按钮隐藏、提交中不重复发送、409／未知网络结果提示正确。
7. 构建和回归：中央相关完整测试、Console前端测试与类型／构建检查、权限回归；不把离线与模拟测试描述成生产结算证明。
8. 浏览器：隔离合成账本上验证队列、详情、进度流转、审计和资金不变。若最终部署，先备份、核对迁移及最小授权，再用本人管理员会话验证；生产旧任务只读验收，不为测试新增处理事件或金融操作。

## R2 预留与本批不宣称的能力

R2需另行明确：新attempt的早期上游关联持久化、供应商适配器能查询的既有事实、可信终态和估算usage的区别、服务端证据归一化与精确绑定，以及独立有权限的金融结算命令。

“只有可信费用、没有原回复”的补结算必须与结果恢复分开，不能造空payload冒充可恢复结果。运营承担损失／补偿、reconciled release、商户付款、自动退款、自动重发、清零未知费用和公开管理访问均不属于R1。

## 审阅结论

已完成中央与Console只读盘点、设计自检及独立核心审阅。已补齐未知提交结果的同actor/job/key只读查询、固定快照摘要、首次revision=0、部分诊断范围及最小按列授权。用户批准后按执行计划实施；旧待核算任务不作为写操作验收对象。
