## 接手时发现的结构问题（影响后续阶段）

1. **订阅媒体与冻结的 B2 耦合**：源码中媒体的每个写操作都要求 B2 维护许可（迁移 017–020 引入的备份写入屏障），而生产仍是迁移 016，没有这套机制。P3 开放媒体前，需要决定保留这层屏障（随 017–020 一起部署）还是剥离为可选。`test_internal_features` 中 2 个图片功能开关测试因此失败，CI 暂时 deselect。
2. **测试套件文件描述符泄漏**：单进程跑全量中央测试会累积 fd，超过 `select()` 的 1024 上限（`test_media_maintenance_*` 报 `filedescriptor out of range`）；CI 暂时拆到独立进程。
3. **测试夹具强依赖冻结工作线的专用设施**（B2 授权文件、Logto 合成身份库、`outputs/_run` 下的本机证据），导致新人无法直接跑通测试。

## 1. 总体目标（据交接手册 01／05 归纳）

1. **创作者价值**：本机工作台 + 内置 Pi，从选题到成品、发布、复盘的内容创作闭环。
2. **订阅商业**：统一账号（Logto）、共享点数钱包、中央模型目录，按量结算；自定义接口长期保留。
3. **可持续运营**：生产数据不丢、账不错，故障可恢复。
4. **可交付**：用户能安装、升级、长期使用的桌面版本。
5. **可扩展**：后续第二产品共享身份与钱包。

### 2.1 投入方向与阶段严重错配（最主要问题）

- 生产中央库归档只有 **约 0.3–0.8 MB**（10-24 真实归档 308,224 字节，10-26 定时归档 830,282 字节）；支付按用户决定处于关闭状态，还没有付费用户。
- 为这一规模的数据，备份恢复写了约 **7 万行**代码和测试，验收深度达到内核网络隔离证明、PID1 二进制身份、900 秒监督进程、ParserAuthority 等，而 B3 仍未完成（once001–005 失败，once008 只通过目标生命周期一项）。
- 10-29 以后的工作几乎全部投在 B2/B3/F2/AV 上，**用户可感知的产品没有进展**：v36 构建后未激活，桌面未签名，创作链路没有新增能力。

### 2.2 真正的数据风险没有被优先关闭

生产已有每日加密 `pg_dump` 定时备份（154，北京时间 03:30），但部署记录明确写着：**仅同机保存、没有异地副本、定时备份从未做过全新恢复、没有告警通知**。也就是说，最大的风险是服务器丢失，而这个风险可以用标准工具在一两天内关闭；旧方案却在本机做一套通用的、尚未完成的重建框架。

### 2.3 自造轮子

- 备份恢复：PostgreSQL 有成熟方案（`pg_dumpall --globals-only` + `pg_dump -Fc`，或 pgBackRest／WAL-G 做 PITR），媒体有 restic／rclone 加对象存储。自研捕获、认证封装、角色导出和重建链路，维护成本极高，只有原作者能看懂。
- AV：从源码构建 FFmpeg 并逐层验证 GPG、libplacebo、Vulkan 头文件和 Ubuntu 安全补丁级别。视频、音乐、语音主要由供应商生成，本地只需要探测和解码；固定版本、带校验和的官方预编译构建即可满足。

### 2.4 过程开销压过交付

- 3 周内约 470 份计划、设计和验收文档，交付总账一个条目往往是数百字的单段文本。新人和用户都很难读懂“现在能用什么”。
- 所有改动都用同一种最高强度的流程（独立复审、冻结哈希、逐项回执），不区分风险。界面文案、媒体组件和资金账本用同一个标准，速度被拖慢。

### 2.5 代码资产不安全

约 15 万行代码和 1,290 个文件从未提交，`codex/ui-redesign` 远程停在 10-15。磁盘损坏、误删或误执行 `git clean`，三周的工作就会全部丢失。另外，Codex 桌面应用仍在运行，两个 Agent 同时编辑同一个工作区会互相覆盖。

### 2.6 交付通道低效

每个桌面版本都要人工在用户机器上激活（v31→v35 各一次），没有自动更新，没有签名公证。

## 3. 优化原则

1. **按风险分级验收**：资金、身份、数据删除和迁移用高强度验收；普通功能用“单测 + 集成 + 一次真实冒烟”；文档和界面用评审即可。不再对每个改动出独立验收文档。
2. **优先用成熟方案**，自研只用于差异化能力（创作体验、订阅结算）。
3. **先关闭真实风险，再追求完备**：异地备份和恢复演练优先于通用重建框架。
4. **小步提交、持续集成**，进度以 git 历史和一份 `STATUS.md` 为准，不再依赖散落的回执。
5. 保留旧方案的正确约束：不伪造用量和付款、未知费用只查原请求、密钥不进客户端、生产操作逐次确认。

## 4.1 P1 细化（基于生产现状）

生产 154 已有 `encrypted_backup.py`（源码：`services/platform/src/platform_service/media_backup_b2/legacy_sources/encrypted_backup.py`）每日运行：两个库的 `pg_dump -Fc`、`pg_dumpall --roles-only`、关键配置文件，整体用 `transfer-public.pem` 公钥封装为 `/var/backups/easel-encrypted/*.sealed`。服务器上没有解密私钥也能产生备份，所以密文本身可以直接异地存放。P1 只需补四件事：

1. **异地副本**：在现有 timer 之后追加一步，用 rclone 把新 `.sealed` 同步到异地对象存储（只追加、不删除，对象存储开启版本保留）。
2. **媒体文件**：中央媒体目录用 restic 加密快照到同一异地存储（restic 自带去重和完整性检查）。
3. **恢复演练**：在持有解密私钥的机器上每周拉取最新密文，解封后 `pg_restore` 到临时 PG16 容器，校验行数、序列、钱包账本恒等式，完成后删除容器；复用已有 `diagnose_encrypted_restore_drill_v4.py` 的解封逻辑。
4. **告警**：备份、同步、演练任一失败或超过 30 小时无新备份时，推送到你指定的渠道（沿用 `easel-health-watch` 的阈值）。
