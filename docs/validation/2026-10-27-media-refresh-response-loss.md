# M4 登录轮换响应丢失诊断

此为认证护栏改动前的 v22 定位快照。后续客户端改动及当前测试见 `2026-10-27-desktop-auth-hardening.md`；当时 d922 测试字节已归档到 `assets/2026-10-27-media-refresh-response-loss-baseline-tests.py.txt`，不把原行为诊断通过计为修复完成。

本次只进行本机代码比对、合成凭据和 loopback HTTP 故障注入，没有读取真实用户的 auth 内容、恢复旧令牌、重新登录、调用生产或供应商，也没有修改产品代码。

## 已复核事实

项目 `easel/platform/media.py`、运行目录 v22 对应文件与 v22 ZIP 内该文件逐字相同，SHA-256 均为 `412b5a17e77cad90f16e29f8b5f5967ef7ae366c211c6b4bcfb59f3d3ec23963`。三个副本都对 `/v2/auth/refresh` 返回保留原始 auth，未经过公共结果 `_safe` 检查。因此“媒体客户端将 fresh auth 当公开结果过滤”的假设被这份运行输入反证。

`IdentityService.refresh` 当前会在数据库事务中消费原令牌、生成新令牌；事务提交后才能返回响应。若下次再次使用已消费的 refresh，服务会设置会话 `revoked_at`，再返回 `401 refresh_replayed`。客户端只在这类明确的 401 后清除本机 auth；网络错误不会立即清除。

## 可重复的响应丢失窗口

新测试 `tests/test_central_media_auth_rotation.py` 使用真实 TCP loopback HTTP，合成服务端按上述消费／重放策略工作，凭据与临时目录全部为测试生成。故障发生在模拟提交之后，分别为响应头已发而正文停顿、正文截断。

| 场景 | 首次本机结果 | 下次自动刷新结果 |
| --- | --- | --- |
| 提交后正文停顿 | 请求超时，原 auth 文件字节保留 | 再用旧 refresh，合成服务撤销会话，客户端收到明确 `refresh_replayed` 后清除 auth |
| 提交后正文截断 | 请求失败，原 auth 文件字节保留 | 同上 |
| 完整响应 | 新 access / refresh 原子保存，scope 保持 | 继续认证成功，无重放或撤销 |

前两种情况各覆盖媒体客户端、文本中央客户端作为下一次刷新方，共四个故障组合。另有真实 ISO 时间字段、access 与 refresh 同时轮换的正常跨客户端对照。

新增六项行为诊断测试全部通过，表示上述当前机制已经复现，**不表示响应丢失后的恢复问题已经修复**。连同现有媒体及中央账号客户端，限定回归为 68 项通过，3.64 秒。测试文件 SHA-256 为 `d9226d1255cb807531f6e4acdd38e3a394c1318c60fe4e52a144c5dc4147b951`。

这证明机制上存在该窗口；本次真实用户事件是否由它触发，仍需由 root 的服务器只读时间线核对。还需排除令牌轮换后旧备份覆盖本机状态，以及多个工作空间复制同一 refresh 的情况。

## 最小修复建议，尚未实施

先在现有跨进程文件锁内持久化一次刷新状态，再发刷新 POST。响应成功且完整校验后，原子保存新 auth 并清理该状态；若传输、正文或本机落盘结果未知，保留与原 scope／refresh 哈希绑定的 `uncertain` 围栏。后续调用不得自动再次发送同一 refresh，而应保留账号上下文、显示认证结果未知并要求明确的重新认证。应用重启也必须遵守同一围栏。

这能阻止第二次自动重放导致会话撤销，但无法从丢失的响应中凭空恢复新令牌，也不能恢复已经被撤销的会话。不得从备份恢复旧 refresh 继续试，不得为了通行而忽略服务器 401。

长期可单独设计短期、严格绑定原操作与设备证明的幂等刷新回执，恢复同一操作已生成的令牌对；需要覆盖凭据加密、重放检测、撤销、权限、备份和到期清理。不能简单取消现有服务器重放撤销保护。
